# Постановка задачи: прогнозирование энергопотребления металлургического завода

## 1. Паспорт проекта
- Название: прогнозирование энергопотребления металлургического завода.
- Описание: спрогнозировать активную мощность электропотребления завода
  по 15-минутным интервалам на основе показателей реактивной мощности,
  коэффициента нагрузки, выбросов CO2 и календарного графика.
- Данные: Steel Industry Energy Consumption (Kaggle), 35 040 записей,
  01.01.2018 - 31.12.2018, шаг 15 минут (96 интервалов в сутки).

## 2. Цели
- Бизнес-цель: планирование энергозатрат и производственного графика,
  снижение пиковых нагрузок и издержек на электроэнергию.
- ML-цель: модель регрессии, прогнозирующая потребление на 1 шаг вперёд
  (15 минут) с качеством, статистически значимо превосходящим наивные
  baseline-модели на единой схеме валидации.

## 3. Формальная постановка
- Один объект: один 15-минутный интервал измерений (одна строка датасета).
- Целевая переменная: Usage_kWh — активная энергия за интервал, кВт·ч.
  Средняя активная мощность за интервал P = Usage_kWh / 0.25 ч;
  прогноз энергии и мощности эквивалентны с точностью до множителя 4.
- Тип задачи: регрессия (прогнозирование временного ряда).
- Горизонт: 1 шаг вперёд (t+1). На момент прогноза доступны история
  измерений до t включительно и календарный график интервала t+1.

### Доступность признаков на момент прогноза
| Группа признаков | Доступность для t+1 | Способ использования |
|---|---|---|
| Календарь: NSM, hour, Day_of_week, WeekStatus, is_weekend, month | Известен заранее | Напрямую для интервала t+1 |
| Load_Type (тип нагрузки из графика) | Предполагается плановым атрибутом | Напрямую; подлежит аудиту (H6) |
| Реактивная мощность и коэффициент мощности (4 признака) | Измеряются одновременно с целью | Только лаги (1, 96 и др.) |
| CO2(tCO2) | Детерминированно связан с целью (corr 0.99, 8 дискретных уровней) | Только лаги; текущее значение исключено (утечка) |
| История цели | Известна до t | Лаги 1, 96, 192, 672; rolling-статистики со shift >= 1 |

Решение по сценарию: nowcast (оценка цели по признакам того же интервала)
отклонён осознанно — текущий CO2 тривиализует задачу, а сценарий не является
прогнозированием. Основной и единственный сценарий — forecast t+1.

## 4. Метрики качества
- Основная: MAE (кВт·ч) — устойчива к скошенному распределению и пикам,
  интерпретируется в единицах цели.
- Вспомогательные: RMSE (штрафует крупные ошибки на пиковых нагрузках);
  WAPE = sum|y - y_hat| / sum(y) (корректна при нулевых значениях цели).
- MAPE отклонён: не определён при y = 0 (воскресенье, простои).
- R2: справочно.
- Формат отчёта: среднее и стандартное отклонение по фолдам + holdout.

## 5. Схема валидации и контроль утечек
- TimeSeriesSplit: 5 фолдов, расширяющееся окно, тестовый фолд 672 записи (неделя).
- Holdout: последняя неделя (672 записи), используется один раз в конце.
- Контроль утечек:
  1. Все лаги и rolling-статистики со shift >= 1 относительно цели.
  2. Scaler и кодировщики обучаются только на train-фолде внутри Pipeline.
  3. Лаговые признаки считаются по отсортированному ряду только из прошлого;
     обоснование отсутствия заглядывания в будущее приводится в ноутбуке.
  4. Случайное перемешивание запрещено.
  5. Текущий CO2 исключён из признаков.
  6. Load_Type проходит аудит на производность от цели (H6).
- Все baseline и модели оцениваются на одной и той же схеме.

## 6. Стратегия предобработки
- Пропуски: отсутствуют (проверено); импутация не требуется.
- Порядок и сетка: сортировка по времени, проверка непрерывности 15-минутной
  сетки, документирование разрывов.
- Кодирование: OneHot для линейных моделей; нативные категориальные признаки
  для LightGBM; сравнение как гипотеза.
- Масштабирование: эксперимент none / Standard / MinMax / Robust на одинаковых
  фолдах для Ridge и Lasso; отчёт по метрике и коэффициентам (число ненулевых,
  величина); объяснение выбранного варианта. Инвариантность деревьев к
  масштабированию демонстрируется отдельно.
- Выбросы: не удаляются (реальные пики нагрузки); робастная функция потерь
  huber; log1p цели как проверяемая гипотеза.
- Аномалии Load_Type (выбросы до 140 кВт·ч в Light_Load): аудит, решение
  документируется.

## 7. Гипотезы feature engineering (проверяются ablation на фолдах)
| ID | Гипотеза | Основание (EDA) | Критерий принятия |
|---|---|---|---|
| H1 | Лаги 96 и 672 улучшают прогноз | Пики ACF на 96, 192, ...; спад в выходные | delta MAE < 0 |
| H2 | lag_1 и rolling-статистики дают краткосрочную динамику | ACF лаг 1 около 0.9 | delta MAE < 0 |
| H3 | Взаимодействия hour x is_weekend полезны линейной модели | Нелинейный суточный профиль | delta MAE < 0 |
| H4 | log1p цели или huber снижают влияние пиков | Правостороннее смещение | delta MAE < 0 |
| H5 | Лагированные CO2 и реактивная мощность добавляют сигнал сверх лагов цели | Corr 0.90 / 0.99 | delta MAE < 0 |
| H6 | Load_Type — плановый атрибут, не производный от цели | Аномалии в Light_Load | Аудит распределений |

## 8. Модели и оптимизация
- Baseline: константа (медиана train); persistence (lag_1);
  seasonal naive (lag_96); Ridge на календарных признаках.
- Основная модель: LightGBM (objective='huber') внутри Pipeline.
- Линейный эталон: Ridge / Lasso (эксперимент масштабирования, коэффициенты).
- Подбор гиперпараметров: RandomizedSearchCV и Optuna (байесовская оптимизация); отчёт о изменении метрики относительно дефолтных параметров и относительно лучшего baseline.
- Интерпретация: важность признаков, SHAP — этап итоговой защиты.

## 9. Требования к коду и воспроизводимости
- Единый Pipeline + ColumnTransformer: вся предобработка и модель внутри.
- RANDOM_STATE = 42 во всех моделях, сплитах и поисках.
- Ноутбук выполняется Restart & Run All без ошибок и вмешательств.
- Чёткая структура Markdown-заголовков; вывод после каждого блока анализа.
- Отсутствие мёртвых ячеек и закомментированного кода.

- Baseline обучен; подбор ГП двумя подходами плюс Optuna; прирост метрики измерен.
- Эксперимент масштабирования выполнен на единой схеме, выбор объяснён.
- Единый Pipeline; RANDOM_STATE зафиксирован; ноутбук проходит end-to-end.
- Целевой ориентир: MAE на holdout лучше лучшего naive baseline не менее чем на 25%.
